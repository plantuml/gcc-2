# gcc-2

Minimal reproduction of a crash of the C generated by TeaVM (0.16.0) when it is compiled by **gcc 15**.
The same C, compiled by gcc 13, gcc 14 or clang, works.

The program ([`Hello.java`](src/main/java/Hello.java)) is a hello world that computes the CRC32 of a
string with `java.util.zip.CRC32`. It must print:

```
Hello, world! CRC32 = ebe6c6e6
```

TeaVM translates it to C (the 177 `.c` files of [`c/`](c), already generated: no Java, no Gradle
and no TeaVM is needed to build them). Built by gcc 15, the executable crashes at the first use of the
CRC32 (a segmentation fault, or an unexpected `NullPointerException`), or not, depending on the size
of the heap.

## Reproduce

Requirements: CMake and a C compiler.

```
cmake -S . -B build
cmake --build build
./build/bin/hello
```

`-DHEAP_MB=n` gives the program a heap of `n` MB (by default the one TeaVM generated, 1 MB to 16 MB).
It changes the layout of the memory, and with it what the failure looks like:

```
cmake -S . -B build-8 -DHEAP_MB=8
cmake --build build-8
./build-8/bin/hello
```

[`.github/workflows/gcc.yml`](.github/workflows/gcc.yml) does exactly this for gcc 15 (the one of
`ubuntu-latest`, Ubuntu 26.04), gcc 14, gcc 13 and clang, and for 15 sizes of the heap, then lists the results in
the summary of the run. Its second job prints how the assembly of the two functions of `CRC32` changes
between gcc 14 and gcc 15.

To generate the C again (JDK 17+, the Gradle wrapper is included): `./gradlew generateC`, the result is in
`build/generated/teavm/c`.

## Results

| compiler | this program | PlantUML (about 4000 generated C files) |
|---|---|---|
| gcc 13.3 (Ubuntu 24.04) | ok, 15 heap sizes (checked by me) | ok |
| gcc 14 (14.2 on Ubuntu 24.04, checked by me; `gcc-14` of Ubuntu 26.04 in the CI) | ok, 15 heap sizes (checked by me) | ok |
| clang (18.1 on Ubuntu 24.04, checked by me; `clang` of Ubuntu 26.04 in the CI) | ok, 15 heap sizes (checked by me) | ok |
| **gcc 15.2 (Ubuntu 26.04)** | **see the runs of the CI of this repository** | **crash** |

I could not run gcc 15 outside of GitHub Actions: the column "this program" for gcc 15 is the result of the
job `hello` (`ubuntu-latest / gcc`) of the CI of this repository, and it is also the answer to the question
"does this reduced program show the problem?".

## How it was found

PlantUML builds a native executable from the C generated by TeaVM, on GitHub Actions. The job of
linux-x64 was green until `ubuntu-latest` became Ubuntu 26.04 (kernel 7.0.0-azure, gcc 15.2.0); the job
of linux-arm64, which is pinned to Ubuntu 24.04 (gcc 13), stayed green. The smoke test, which draws a
mind map as a PNG, crashed. Traces added to the program showed that it was not the PNG: the first use of
`java.util.zip.CRC32` already failed, before anything else was done:

```
[trace 1] start, arguments: -tsvg mindmap.puml
[trace 2] start: heap free=67078840 total=67108864
Segmentation fault (core dumped)
```

What was found with the executable of PlantUML (same C, gcc 15.2 on Ubuntu 26.04):

* Variants of the same job: **gcc 13, gcc 14 and clang on Ubuntu 26.04 are green; gcc 15 is red.**
* `-fno-strict-aliasing`, and `-fwrapv -fno-delete-null-pointer-checks`, do not help.
* The result depends on the size of the heap, and on the code of the program, but not in a monotonic way. Heap
  of 16, 32, 48, 64, 96, 128, 192, 256, 512 and 1024 MB, `-tsvg` / `-tpng`: crash / crash, crash / NullPointerException,
  ok / crash, ok / crash, ok / crash, ok / crash, crash / NullPointerException, crash / NullPointerException,
  crash / crash, ok / crash. Without address randomization and with an empty environment it is the same.
* valgrind (3.26): `Invalid read of size 4`, in `CRC32.update`, `Address 0x8 is not stack'd, malloc'd or
  (recently) free'd`. The field `v` of the jzlib `CRC32` is at offset 8: `this` is NULL.
* gdb: the flag "class initialized" of `com.jcraft.jzlib.CRC32` goes from 0 to 1 (the static initializer starts), then
  `SIGSEGV` with **the program counter at `0x00007fffffffbfe0`, an address of the stack**: the program jumped to
  the stack, as after a return or a `longjmp` to a frame that does not exist anymore. valgrind also shows a
  call stack made of garbage (`by 0x1FFEFFDF7F: ???`).
* No garbage collection, and no memory problem: at that point 30 KB of a heap of 64 MB are used.

## The code that fails

`new CRC32()` in Java is, in C (`c/c/j/u/z/CRC32.c`, the wrapper of `java.util.zip` of TeaVM):

```c
void meth_juz_CRC32__init_(void* teavm_this_) {
    void* teavm_local_1;
    TEAVM_ALLOC_STACK(INT32_C(1));
    TEAVM_GC_ROOT_RELEASE(INT32_C(0));
    teavm_local_1 = TEAVM_WITH_CALL_SITE_ID(32777, meth_otr_Allocator_allocate(&cjj_CRC32_Cls));
    TEAVM_GC_ROOT(INT32_C(0), teavm_local_1);
    TEAVM_WITH_CALL_SITE_ID(32778, meth_cjj_CRC32__init_(teavm_local_1));
    teavm_gc_writeBarrier(teavm_this_);
    TEAVM_FIELD(teavm_this_, cls_juz_CRC32, fld_impl) = teavm_local_1;
    TEAVM_RELEASE_STACK;
}
```

`TEAVM_ALLOC_STACK` is a local structure (the "shadow stack" that the garbage collector walks), whose address is
stored in a global:

```c
#define TEAVM_ALLOC_STACK(sz) \
    struct { TeaVM_StackFrame header; void* data[(sz)]; } teavm_shadowStack; \
    teavm_shadowStack.header.next = teavm_stackTop; \
    teavm_shadowStack.header.size = (sz); \
    teavm_stackTop = &teavm_shadowStack.header
#define TEAVM_RELEASE_STACK (teavm_stackTop = teavm_shadowStack.header.next)
```

Exceptions are `setjmp`/`longjmp`, and a null check is:

```c
inline static void* teavm_nullCheck(void* o) {
    if (o == NULL) {
        teavm_throwNullPointerException();
        __builtin_unreachable();
    }
    return o;
}
```

## What is not known

The cause: whether it is an undefined behavior of the generated C that gcc 15 now exploits (the shadow stack,
`__builtin_unreachable()` after a call that does not return normally, or the objects that are accessed through
the type of their class), or a bug of gcc 15. This repository exists to have the smallest program that shows it, and
to see what gcc 15 does differently (job `assembly`). Hypotheses are not checked: none of them was tested with gcc 15.
